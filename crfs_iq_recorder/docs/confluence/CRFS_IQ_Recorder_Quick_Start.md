# CRFS IQ Recorder - Quick Start Guide

CRFS IQ Recorder is a Windows app for CRFS sensors. It starts an IQ recording, downloads the WAVE files to this computer, and shows a short waterfall preview so you can check that a signal was captured.

## Download and run

**Version:** 1.19.0
**File:** `CRFS_IQ_Recorder.exe` - one file, no Python, no install. `CRFS_IQ_Recorder_Setup.exe` - installer for company-managed PCs (installs to Program Files, Start-menu shortcut). With the installer, keep the default folder: do not install into Documents, Desktop or Pictures - Windows ransomware protection guards those folders and can block the uninstaller there.

> Windows EXE: [CRFS IQ Recorder 1.19.0](https://github.com/ItayHararii/iq-spectrogram-converter/releases/tag/v1.19.0)

1. Save the exe on this PC (Desktop or a local folder).
2. Double-click **CRFS_IQ_Recorder.exe**. The window opens in a few seconds; sensor details fill in afterwards.
3. This computer must be able to reach the sensor on the network.

**"Windows protected your PC"** can appear the first time you run a new version. That is Microsoft Defender SmartScreen saying the file is new to it and is not signed by a publisher it knows; it is not a virus detection. Check that you downloaded the file from the GitHub Release link above, then choose **More info -> Run anyway**. Do not turn off SmartScreen or Defender for this.

**The app does not start at all** on some Windows 11 PCs (Smart App Control on) and on company-managed PCs (App Control / AppLocker). Unsigned software is refused there by design; releases become signed once the Sensorz code-signing enrollment is complete. Until then: on a company PC, ask IT to deploy `CRFS_IQ_Recorder_Setup.exe`; do not turn off Smart App Control. To see which protection is involved, run `diagnose_block.ps1` from the project folder `packaging` next to the downloaded file and send the report it writes to the Desktop.

**Taskbar icon:** the app uses the Sensorz icon. If a pinned shortcut still shows an old or blank icon after an update, unpin it and pin the running app again (Windows caches shortcut icons).

Do not put real sensor IPs, logins, or passwords on this page or in screenshots.

## Record IQ

The window has two tabs under one sensor header: **Manual Recording** (one recording or a series) and **Excel Collection** (the rows of a protocol workbook). Only one of them uses the sensor at a time; while one runs or is paused, the other tab's Start is disabled and a line under it says why (for example *Excel Collection is running.*). Switching tabs never interrupts anything. The last tab and the form values come back at the next start; nothing starts by itself.

1. Open **Settings** and enter the sensor IP, HTTP login, and SFTP login.
2. Check **Model**, **Firmware**, **Serial**, and **Status** in the header. Status should read **Connected**. The same text is shown at the bottom left. The app checks the sensor every 10 seconds. After one missed check the badge turns amber **Reconnecting...**; after two it turns red **Disconnected**. It returns to green **Connected** on its own when the sensor answers. SFTP problems stay in Sensor Files and are not treated as an API disconnect.
3. Choose **Start / End** or **Center / Bandwidth** (values in MHz).
4. Enter **Recording time (s)** and check **Estimate**.
5. Click **Start Recording**. Only a click (or **Space** after moving to the button with **Tab**) starts a recording; **Enter** in a field never does. Status goes **Sending request…**, then **Recording**, then **Waiting for files** while the app waits for the sensor's files, then **Files ready**. If the sensor finishes but no file appears, the status says so instead of reporting a completed recording. Large recordings stay in **Waiting for files** for a while: 2 s at 60 MHz on a Node 100-18 is about 1 GB, which the sensor needs about a minute to write (longer while other files are downloaded). The app waits until the sensor has finished the file; closing the app earlier makes the sensor cut the file short.
6. The **Last recording** card shows what happened in three short lines: the range (`758-768 MHz`) with a tag (**Complete**, **Partial**, **Uncertain**, **Failed** or **Other range**), the facts read from the files (`1 file · 0.536 s · 33.5 MB`, or *duration unknown* when the file could not be read) and the states (`Recording complete · Download saved`). When the sensor recorded a different range than requested, one more line says so (`Sensor reported 3500-3600 MHz (100 MHz), not the requested range`; the Node 100-18 records at most 100 MHz around the centre). **Partial** means the files hold more than 2 % less time than requested. **Download** copies the files to this PC into a folder named after the sensor's recording day (`Recordings\20261104\`); **Open folder** opens that folder with the file selected once the copy has been verified. The waterfall is in **Sensor Files**.

To log into a collection workbook: tick **Log each recording to an Excel log workbook (.xlsm)**, choose the `.xlsm` file, and check the collection event and target class. When a recording finishes, the app adds that capture to the Excel log automatically (class, frequencies, filename, and Playback Start as `N seconds`). Split parts stay on the same row.

**Repeat recording** (a count or **Until stopped**) runs consecutive recordings, with a wait between them (default 5 seconds). **Pause** finishes the current recording and waits; **Resume** continues (time spent paused counts toward the wait). **Stop** finishes the capture that is already running, or cancels the countdown, and does not start another.

**When something goes wrong:** the activity log beside the form gives one short sentence per step. Right-click the activity log for **Open diagnostic log** (exact requests, sensor replies, errors) and **Copy diagnostic details**, which puts a report on the clipboard for support: app version, sensor model and serial, the last request and its reply, and the latest log lines. The sensor's address, other addresses, your user folder, the sensor's position and stored passwords are masked in it.

HTTP and SFTP logins are remembered on this computer. In Sensor Files, select files and press Delete (or right-click **Delete from sensor…**) to remove them from the sensor; a confirmation is shown first.

## Find and download recordings

1. Click **Sensor Files**.
2. Today's folder on the sensor opens (`/mnt/1/remdata/YYYYMMDD/`). New files show **NEW**. A split capture appears as a collapsible parent such as `iq_20260915_142718`, with `_0001.wav` and `_0002.wav` underneath. Single files stay as normal rows.
3. **Req. start / end / center / bandwidth / duration** are what was requested (from this app's recording history). **Recorded (MHz)**, **Recorded (s)** and **Rate (MS/s)** are read from the file itself (its header and CRFS metadata) once the app has read it: when it was recorded, previewed or downloaded. Until then they say *unknown*. A 500 MHz request on a Node 100-18 shows `Req. bandwidth 500` and `Recorded 3500–3600`. Sizes are decimal (1 MB = 1,000,000 bytes); hover a size for the exact bytes and MiB. The parent shows part count and combined size.
4. Select the parent and click **Download this recording** for every listed part, or select individual children to download only those files. There is no save dialog; files are saved under the recordings folder in a subfolder named after the sensor's recording day (`20261104\`), parts of one recording together. The **Local copy** column shows *Saved*, *Queued*, *Downloading* (with speed and time left once measured), *Waiting to retry*, *Verified* or *Failed*. A file already on this PC with the same size is not downloaded again (no `(2)` copy); a different local file with the same name is kept, and the download goes into a subfolder named after the sensor, or gets a new name. Connecting and waterfall stay in the background, so you can still move, resize, or close the window, and **Open recordings folder** works while a sensor connection is pending.
5. **Right-click** a file or folder to see what you can do with it. Right-clicking a row that is not selected uses only that row; right-clicking inside a selection uses the whole selection. Actions that cannot be used right now are greyed out and say why (for example *Downloads in progress* or *Not downloaded yet*).
   - **Download** copies the selected files to the download folder; **Retry download** appears after a failed one.
   - **Open folder** opens the folder on this PC where the file was downloaded, with the file selected. It is available once the file has been downloaded.
   - **Copy filename** copies the selected names, one per line.
   - **Delete from sensor…** deletes the selected files from the sensor (also the Delete key). Copies on this PC are kept.
   - On a folder: **Open** shows its contents, **Open local folder** opens its downloaded copy on this PC, **Copy folder name** copies the name, and **Delete folder…** deletes it.
6. **Delete folder…** first counts what is inside, then asks once. The question shows the sensor (model, serial and address), the full path, and how many files, subfolders and links it holds; **Cancel** is the default, and deleting cannot be undone. Only folders inside the recording folder (`/mnt/1/remdata/`) can be deleted, never the recording folder itself. Links are removed as links; what they point to is never touched, and a folder that is itself a link cannot be deleted. Deleting is refused while a recording or a collection runs, while a download from that folder runs, or when something in the folder was written in the last 2 minutes. A progress bar counts the items; **Cancel** stops after the current one. If some items cannot be deleted, the app says how many were deleted and which ones failed, and keeps the folder. Copies on this PC are always kept, and the status line says where they are.

Default local folder: `%USERPROFILE%\CRFS IQ Recorder\Recordings` on the local disk, not OneDrive. Change it in Settings.

The main window shows **IQ Storage** for the sensor disk that holds `/mnt/1/remdata/`. It refreshes on connect, while connected, and after a recording or a remote delete. Under 10% free is a yellow warning; under 5% is red. A recording that would not fit, including a safety margin, is blocked. Existing files are never deleted to free space.

Change it in **Settings -> Download folder**. The choice is remembered. Files stay on this PC (not OneDrive or other cloud folders).

## Spectrograms

After each IQ file is downloaded and verified (from **Manual Recording**, **Excel Collection** or **Sensor Files**), the app makes its spectrogram in the background with the IQ Spectrogram Converter engine and its saved settings: a full-size PNG and a small thumbnail in a `Spectrograms` folder beside the WAV (`Recordings\20261109\Spectrograms\`). The frequency axis is absolute MHz when the file carries its centre frequency, and the requested range is drawn as dashed markers. The recording itself is never changed. Activity shows **Generating spectrogram** and then **Spectrogram added.** (or **Spectrogram saved** when no Excel row lists the file). If a spectrogram fails, Activity shows **Spectrogram failed: <file>**; the detail is in the diagnostic log, and recording carries on. Large files take a few minutes (about 5 minutes for a 2.3 GB recording). Waiting spectrograms survive a restart of the app, and a file is never converted twice.

**In Excel.** Every row that lists the IQ file (the Excel log and the Excel Collection results) gets a thumbnail in an **IQ Spectrogram** column directly right of **IQ Recording**. An existing IQ Spectrogram column is reused; an empty column there is used as it is; otherwise Excel itself inserts the column once, so formulas, formats and tables stay correct. A recording in several parts gets one thumbnail per part, side by side. Thumbnails move and size with their row, so sorting and filtering keep them with the right file. Click a thumbnail to open the full-size PNG. If the workbook and the PNG are both in a OneDrive or SharePoint folder that this PC syncs, the link is the SharePoint address; otherwise it points to the file on this PC, and its tooltip says so.

When the workbook is open in Excel, thumbnails are added there and the workbook is saved. While you are typing in a cell or a dialog is open, they are added a few seconds after Excel is free. A closed workbook is updated directly only when that is safe (a backup is made first; macros, formulas and existing pictures are kept); otherwise its thumbnails are added the next time it is open in Excel, and Activity says so once. No thumbnail? Open the workbook in Excel and wait up to a minute. A row hidden by a filter gets its thumbnail once the filter is cleared. The PNG is always in the `Spectrograms` folder beside the WAV.

## Merge split recordings (optional)

The sensor closes a recording file every 500 MB and continues in the next numbered part (`_0001.wav`, `_0002.wav`, ...). At 25 MHz bandwidth that is about 4.2 seconds per part. The parts are one continuous capture; this is a setting on the sensor, not in the app.

- Tick **Merge recording parts** in the main window to have every fully downloaded split recording joined into one file automatically. The option is off by default and is remembered. Untick it to stop new merges; **Cancel merge** stops the one that is running.
- Or select a recording in Sensor Files and click **Merge parts**. Parts that are not on this PC yet are downloaded first. The confirmation shows the parts, the verified duration, the output size, and the folder.
- The result is `<recording>_merged.wav` in the download folder, next to the original parts, which are kept. A `.merge.json` file next to it lists what was joined and the join checks. Open the merged file in IQ Spectrogram Converter like any other WAVE file; files over 4 GB are written as RF64, which the Converter reads.
- The app checks that the parts belong together (same frequency window, sample rate and format, numbered without gaps, each part starting where the previous one ends) before it writes anything. If something does not match, the merge is refused and the reason is in the log; the recording and the downloads are not affected.

## Excel Collection (optional)

Records the frequency ranges listed in your protocol workbook, row by row, and repeats the whole list as often as you want so activity can be compared at different hours. Open the **Excel Collection** tab. The badge beside the title shows the state: **Idle** (no plan yet), **Ready**, **Recording**, **Waiting**, **Scheduled**, **Paused**, **Finished**, **Stopped** or **Interrupted**. While a collection runs or is paused, the Manual Recording tab's **Start Recording** is disabled with the reason under it, and the other way round.

The form reads top to bottom in the order you work: Excel file and worksheet, **Open written Excel file** and **Check readiness**, recording duration and wait, **Run now** or **Schedule**, and the action bar - **Preview**, **Start**, **Pause** / **Resume**, **Stop** with the one-line status - which stays visible under the form while it scrolls. Problems are shown in the summary itself and listed in **Preview**. **Check readiness** runs the same checks as Start (sensor identity, clock, storage, destination, plan, workbook) and answers in one line without recording anything. **Open written Excel file** opens the workbook that received the results (the one already open in Excel is brought to the front); it is disabled until a result has been saved.

1. **Excel file and worksheet.** Click **Browse…** and pick the protocol workbook (`.xlsx` / `.xlsm`), then choose the worksheet. Each row is one recording: **Band**, **Direction**, **Duplex**, **Freq Start (MHz)**, **Freq Stop (MHz)**. The summary reads like `15 rows · 2 s per request · 10 s between recordings · 1 pass`; a row the app cannot use is listed in **Preview**, and Start stays disabled until it is fixed. **Reload** re-reads the workbook after you edit it.
2. **Recording duration** is set here, in seconds, and applies to every row. **Wait between recordings** is 10 s by default.
3. **Start: Run now** records the list once, or **Repeat** it a number of times / **Until stopped**, with the same wait between passes. **Schedule** shows the date, **Repeat daily** and the start times: **Add time** (beside the list) opens a time picker with hour and minute wheels and presets, each time has its own × to remove it, and the date field opens a calendar. Times are this computer's local time, shown in the Windows date and clock format; nothing has to be typed. The application must be running and the computer awake; a pass that was missed because the computer slept or the app was closed is reported when the app is back (**Run the missed pass now** or **Skip it**), and the log says when the computer was asleep. Passes never overlap: the next one starts only after the previous one has finished.
4. **Preview** shows the rows in worksheet order with the range requested for each. Every row is **one request** to the sensor, sent exactly as the row says (centre and bandwidth of its Start/Stop range, the chosen duration). What the sensor actually recorded is read from its files afterwards and shown in the result: a sensor that records less than requested (the Node 100-18 records at most 100 MHz around the centre) gives **Other range**, a recording shorter than requested gives **Partial**.
5. **Start** first checks which sensor is connected (model and serial; the plan is tied to it), shows the preview, and starts. The status line reads `Recording row 1 of 15: 703-713 MHz` or `Next recording in 10 s`; the **Last recording** card shows the row, its tag, `Requested` / `Received` / `Recorded`, and whether the files are downloaded and the workbook updated. While downloads lag, the line under the status says `Downloads: N waiting`; when too many wait, the collection pauses until they catch up and says so. If the sensor stops accepting new connections (seen over VPN after many connections in a few seconds), downloads wait and try again on their own; after 10 minutes without a connection they stop and the files stay on the sensor. A file counts as downloaded only after the local copy has the sensor's size and the same samples as the file on the sensor. **Pause** finishes the current recording and waits; **Resume** continues; **Stop** finishes the current recording and records nothing else. Before every request the app checks that the sensor is free. Recordings and downloads take turns on the sensor's disk: no download starts while a recording is made, each recording's files are downloaded before the next request, and the next recording also waits until the sensor has written the previous one to its disk (*Next recording after the downloads that are running*, *Waiting for the sensor to finish writing to its storage*). Downloads started in Sensor Files count too. On a Node 100-18 at 60-75 MHz (125 MS/s) a 5 s row then takes about 6-10 minutes, and its file holds about 4.8-5.0 s: that is the sensor's own limit at this rate, shown as recorded (under 4.9 s the row is **Partial**).
6. **End of a pass.** A summary shows `Completed 14 · Partial 0 · Failed 1 · Uncertain 0`. **Retry failed rows** first checks any uncertain row with the sensor (a row whose file turns up counts as recorded and is not sent again), then sends only the failed rows again, unchanged (`attempt 2`). Completed and partial rows are kept. A failed attempt writes nothing to the workbook, so the retry fills the same row. Nothing is ever re-sent on its own. Files that could not be downloaded are listed (`Not downloaded: 3 files, still on the sensor.`); **Retry downloads** downloads them again and records nothing.
7. **Downloads finish before the next collection.** A new collection can start only when the last one has finished downloading (Start says *The last collection is still downloading…*). If the app is closed before the downloads finish, it says so at the next start; **Continue** downloads the rest (the files are still on the sensor) and sends nothing.

If the app or the computer stopped during a collection, the next start shows what was interrupted. **Check with the sensor** looks for files of recordings that were not confirmed, **Continue** finishes the pass, and **Dismiss** hides the notice; nothing is sent again without you pressing a button.

**Window layout.** The activity log sits beside the form; drag the dotted handle between them to resize it, or use **Hide log** / **Show log** in the header (dragging the log shut does the same). The moon / sun button switches between the light and dark theme.

**What is written to the workbook.** Only the protocol's own nine columns are used, plus the **IQ Spectrogram** thumbnails (see [Spectrograms](#spectrograms)): **Band, Direction, Duplex, Freq Start (MHz), Freq Stop (MHz), Sensor, IQ Recording, IQ Duration (s), Recording Date & Time**. The first pass fills the empty result cells of the protocol rows themselves; every further pass appends the same rows as a new block below the last used row of the same worksheet, with the frequencies copied (still numbers, shown with *MHz*) and its own results. **Sensor** is the connected sensor's verified identity in readable form (`CRFS 100-18`), **IQ Recording** lists the recording's files one per line (split parts of one recording stay together), **IQ Duration (s)** is the measured seconds as a number (`2.011`, not rounded), and **Recording Date & Time** is the actual local capture start as a real Excel date and time shown as `dd/mm/yyyy hh:mm:ss`. No Window, Status, Notes or Round columns are added and no new worksheets are created; earlier results and anything you typed in the workbook are kept, because the app only writes the cells of its own rows. A `.crfs-backup-<date>` copy is made before each collection's first change of the workbook; if the backup cannot be made, nothing is written and the panel says so. If the workbook is open in Excel, the results are written through Excel into the open workbook (your unsaved edits stay), also when several Excel windows are open: the app finds the one that has this file. While you are typing in a cell, or the workbook is open read-only, the results wait and are written afterwards; if another program is holding the file in a way that blocks writing, the results wait (*N Excel update(s) pending*) and are written when the file is free - also after the app is restarted, and also when the collection itself has already finished. If the workbook cannot even be opened when you press **Reload** or **Start** (locked, drive unplugged), the rows imported earlier from it stay the plan and the results are queued the same way; the panel says so.

Technical details per capture (exact window frequencies, requested and measured seconds, UTC timestamps, sensor serial and firmware, file sizes and SHA-256) are kept outside the worksheet: in the `<recording>.cellular.json` manifest beside the downloaded files, in the session state and the Excel queue under the app's configuration folder (`cellular\session.json`, `cellular\workbook_queue.json`), and in the handover summary (`cellular_manifests\handover_*.json` / `.md`) written at the end of a session. Nothing is uploaded anywhere and no recording is deleted automatically.

## Preview the captured signal

Click a WAVE or XDAT file. A short waterfall of the first portion appears under the list (frequency on X, time on Y, colour in dBFS/bin). Use it as a quick visual check; it reads only the beginning of the file, so a quiet start does not mean a quiet file.

- **Zoom the time axis** with the mouse wheel over the picture; the time under the pointer stays where it is. **Drag** up or down to pan. **Reset view** (or the Home key) shows the whole sample again; the button is enabled only while you are zoomed in. A small badge in the corner reads the zoom factor and the visible span.
- **Point** anywhere on the picture to read the exact time (local clock from the file's own start time, plus the offset into the sample), the frequency in MHz and the level in dBFS/bin on the line under the picture.
- The frequency axis is absolute RF only when the file carries its centre frequency (CRFS metadata in a WAVE, or the `.xhdr` beside an `.xdat`). The range requested for that recording is drawn as dashed markers; a part of the requested range the file does **not** cover is drawn **hatched grey**, and the line under the picture says what is covered (`File covers 700.19-715.81 MHz of the requested 691-721 MHz; hatched … not recorded`). Without a centre in the file the axis is relative to the centre and the requested range cannot be placed.
- `.xhdr` and `.xmrk` files hold no samples; select the `.xdat` beside them. An `.xdat` whose header the sensor has not written yet says so - select it again a moment later.

## Sensor clock

The app compares the sensor's clock with this computer's clock (allowing for the network delay and the time zone) when it connects, before each collection and when a recording reply looks misdated. It only trusts the comparison when this computer's clock is itself verified (internet time or the Windows time service). If the sensor is more than 2 minutes off and idle, Activity shows **Sensor clock incorrect - refreshing NTP**, and the app refreshes the sensor's time service by saving its Network Time page twice: first with a temporary extra copy of the first server, then with the original list, so the settings end unchanged. It reads the page back to make sure, then checks the time for up to 90 s and shows **Sensor clock synchronized.** only when the clock is right. A refresh takes about 15-20 s; the sensor's web page does not answer while it saves, and the connection badge is not affected. The app never switches NTP on, never acts while a recording is running or finishing, tries at most twice, then waits 30 minutes. A collection recording waits for a running check (up to 4 minutes). If the app is closed during a refresh, it puts the server list back at the next start.

Other messages: **Sensor clock still wrong after NTP refresh** (new recordings will be misdated), **Could not refresh NTP on the sensor.**, **Sensor NTP server list not restored.** (the diagnostic log names the list to put back on the sensor's Network Time page), **Sensor NTP server list restored.** (an earlier refresh was finished), **Sensor clock incorrect - NTP is off on the sensor.**, and **Sensor clock looks wrong, but this computer's clock is not verified.**

While the sensor's clock is wrong it names its date folders by its own date (for example `/mnt/1/remdata/20120102/`). The app looks in the folder the sensor reports, so recordings are still found and downloaded (into a folder with the sensor's date). A sensor that keeps losing its time after a power cut may have a flat clock battery.

## Useful notes

- Recordings are saved on the sensor first. **Download** copies them to this computer.
- Status in the header and at the bottom left is the sensor API link. SFTP errors are shown in Sensor Files.
- Today's sensor folder is created after the first recording task is submitted.
- Recordings over 500 MB are split into numbered files by the sensor. The parent row represents the whole capture; download or delete that parent if you need every listed part, and use **Merge recording parts** or **Merge parts** to join them on this PC.
- With Excel logging on, each finished recording is added to the workbook automatically.
- The waterfall preview is a short overview of the start of the file.
